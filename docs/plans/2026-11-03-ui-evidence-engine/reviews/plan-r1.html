Technical details

What you approve

Agreement r1 is proposed and not agreed. Questions U1 to U4 are open. Nothing is built before you agree to the behavior and approve the plan.

What was asked

Show real screens and real components in plan reports wherever that can be done safely. Link every element to its real source and approval status. Refuse visual approval when an accurate picture is not possible.

This is a new, separate task from the owner's request of 2026-11-03.

What will happen

Agreement r1 covers the requirements R1 to R10, the architecture and the boundaries. U1 to U4 are open. If U3 is (b), U-T6 is dropped and Cheflabels keeps sketches. U-T8 then checks Altinstar only.

workflow-axa gets a framework-neutral evidence contract. Each capture has one manifest with the image, viewport, component and variant, approval status, decision IDs, runtime problems and dependency fingerprints. The renderer accepts a real preview only with a valid manifest.

Adapters behind one interface discover, render, capture, report runtime problems and fingerprint dependencies. The planned adapters are static HTML, Angular/Ionic for Cheflabels and React/Vite for Altinstar. Unity and other non-DOM screens use a manual capture, or visual approval is blocked.

Not included: application code changes, invented UI, installs, production contact, pixel blurring and capture of screens with personal data.

Decisions made

Four questions are open: U1 architecture, U2 browser automation, U3 Cheflabels offline kit capture and U4 machine-readable approval status. The recommended answer for each is (a).

The recommended architecture builds the contract and element verification first, then exactly two real adapters. Two real users justify a shared interface. With only one, the interface is a guess.

What stays the same

  • Approved and candidate components stay distinct.
  • No application code changes in this task, and no invented UI to make a preview work. Anything a project needs is proposed to its owner as a separate task.
  • No invented HTML, CSS or SVG for application UI. D14 stays, and the report shell keeps the owner's design.
  • Visual approval is blocked when an accurate picture is impossible.
  • No production contact during capture and no installs.
  • No screen that shows personal data is captured. No pixel blurring is promised.

Risks and open questions

Risks and limits

  • The Cheflabels kit page still loads translations over HTTP, and its development environment points at the live backend. A capture without an offline configuration contacts production.
  • Other risks are committed tokens in environment files, personal data in captures, running project code to capture, and fidelity limits. Examples of fidelity limits are the 500 px minimum width, fonts, Ionic md and iOS modes, and WebView differences.
  • Some screens cannot be captured without a server or device. They keep sketches and block visual approval.

Open questions

Work starts after these are answered.

  1. Q1 U1 Architecture. (a) Contract and element verification first, then two real adapters (Cheflabels, Altinstar). Recommended. (b) The full adapter engine at once. (c) Kit routes only: capture only approved kit pages.

  2. Q2 U2 Browser automation. The engine needs an installed browser automation tool (Playwright). Altinstar has it and Cheflabels does not. (a) You install it where you want real previews, and the other projects keep sketches (recommended). (b) Use the installed Edge in headless mode only. That gives screenshots but no console or network records.

  3. Q3 U3 Cheflabels offline kit capture. A safe capture of the kit page needs an offline configuration and a fixture translation file in Cheflabels. (a) A separate Cheflabels task with its own gates. Recommended. (b) Not now, and Cheflabels keeps sketches.

  4. Q4 U4 Machine-readable approval status. Approval status now lives in a Markdown table (Cheflabels DESIGN.md). (a) The adapter reads that table as it is, with no project change. Recommended. (b) Each project adds a small JSON status file.
