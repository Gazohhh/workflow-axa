Reference

Context and scope

You agreed to Agreement 2 with nine adjustments (D24 to D34). Agreement 3 adds the acceptance items A12 to A15. You agreed to it with "go" (D35).

Instruction files on your repositories differ in size and shape. Documentation is scattered, and nothing checks it against the code.

The workflow skills say the same rule in many places and use several words for one thing. You get many questions with obvious answers.

This plan builds one short entry point, a documentation check, lighter rules and better questions. Nothing that protects you today is removed.

Goals and non-goals

Goals

  • A configured repository has a short AGENTS.md with rules, commands and an index of documents with "read when" lines.
  • An agent reads only the documents a task needs and keeps them true to the code.
  • The delivery lists each affected claim as verified, contradicted or not verified.
  • Each rule is stated once, in one vocabulary.
  • Genuinely small changes take a lighter route that keeps your approval.
  • You get fewer, better questions.

Non-goals

  • Rewriting any project repository. The trial writes proposals only.
  • A documentation generator, a generated manifest, or a mapping of every source file.
  • Disabling plugins automatically.
  • An ADR, unless a lasting trade-off is not already in DECISIONS.md.

The design

Overview

Rule-maker becomes the owner of project instructions and documentation, with three operations: audit, apply and check. A small script does the checks a machine can do.

The script follows links from AGENTS.md, finds related documents through links and folders, and checks named paths, commands and versions. The agent checks the meaning of each affected claim.

Hook changes are built in a copy, tested against real failures, and copied back in one step.

The wording pass runs last, split by folder, so parallel workers never edit the same file.

Flow reviewed for r1. The "Today" view shows the code before the change. The proposed view is what was built. The checks below show what was verified.

Constraints

  • All approval gates, safety hooks and blocking protections, and the duplicate guard.
  • The shared standards library and its global imports.
  • Vendored upstream text, byte for byte.
  • Your report patch in skills/codebase-map.
  • Every project repository outside this one. The trial only reads them.

Alternatives considered

  • The AGENTS.md index is the manifest. Not chosen: a generated manifest, because it would be a second copy that drifts.
  • Relationships come from links and folders. Not chosen: a hand-kept file-by-file mapping, which you ruled out.
  • Rule-maker is extended. Not chosen: a new skill, because the responsibility belongs together.
  • A separate script for documentation. Not chosen: extending readiness.py, whose job is different.
  • The gate keeps its stop in every unclear case. Not chosen: attributing an edit to a task whose paths are unknown.

Cross-cutting concerns

  • The hook changes touch the approval gate. Every existing protection keeps its tests, and new adversarial tests are added first.
  • The spending cap works per call. A call already running when a cap is reached can still finish, so the plan keeps one dollar of headroom.
  • The reported cost is an estimate at API prices. On a subscription account it is not the amount billed.
  • Codex is not installed here, so it is checked against its documentation only.
  • The audit proposals quote private project content and stay in an ignored folder.

How it was tested

Each script and hook change gets a failing test first. Fixtures with deliberate problems prove that each check detects them.

Fresh subagents test the new instructions on fixtures: the claim review, the purpose statement and the questions.

The full suite runs after the hooks are copied back and after the wording pass. An independent reviewer checks the whole result.

Then at most 5 capped live sessions, and two checks only you can do.

Order of the work

First, in parallel: the failure reproduction, the guard addition, the documentation script and the archive.

Then the hook changes in a row, and the rule-maker redesign with the phase steps.

Then the small-change prose, the wording pass by folder, the test updates and the release.

Last, the read-only trial on your repositories and the capped live runs.
