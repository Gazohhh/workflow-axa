# Resolve authority without rewriting intent

Read when instructions disagree, a policy change is proposed, or a full rule audit is requested. Host/organisation safety and permissions remain binding. This file is a decision procedure, not a claim that every agent host mechanically resolves precedence the same way.

## Establish the actual sources

Identify the current explicit user direction, effective project/scoped instructions, approved task decisions, shared defaults and relevant memory/history. Record source, scope, date/revision when known and status (approved, proposed, superseded, historical). A filename, newer timestamp, recommendation, unchecked TODO, model summary or memory does not authenticate approval. Do not infer consent from silence or unanswered options.

Memory is a lead to investigate, not independent authority to replace a current agreement. For example, an old note about avoiding extra documents during a build must not silently replace a project's create-or-reuse task-record policy. Show the competing statements and their scopes; preserve the current valid policy unless an authorised user explicitly changes it. Do not "repair" memory or delete it without separate permission. Point lasting preferences at their authoritative shared/project rule rather than creating another copy.

Explicit approved project constraints may specialise shared defaults, but unexplained safety, ownership or permission conflicts stop affected actions. Ask only about the actual unresolved decision; reuse settled answers. Do not choose the less restrictive rule or claim that "repo always overrides global" across hosts. Discovery and read-only diagnosis can continue within access rights.

## Review proposed changes as changes to behaviour

Show current rule, proposed rule, reason, affected work and required authority before applying. Formatting or moving a rule must preserve its meaning, links and line endings. An unanswered follow-up leaves that question unresolved, even if another change was approved. Updating shared rules does not silently rewrite repository rules or migrate old records.

Avoid overbroad policies: "always 20 subagents" can conflict with a quiet profiling host; "retain all setups" may have a narrower scope than disposable output cleanup; "ask every choice" can conflict with approved delegated details. Establish scope rather than erasing either instruction. Do not invent work to fill slots or use measurements from an intentionally noisy host as clean performance evidence.

Use normal accurate language such as component, API and service where appropriate. Preserve established domain terms without forcing specialist jargon on nontechnical readers. Comments may be as long as an important safety/API explanation needs; assess runtime impact before demanding performance work. Where existing policy is stricter, propose its change rather than ignore it.

Keep resolutions in existing PLAN/DECISIONS or the authoritative policy. No new conflict registry for ordinary work. Pass resolved constraints and unresolved boundaries to workers; a specialist's preferred architecture is not permission to replace them.
