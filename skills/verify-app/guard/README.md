# The guard

The guard keeps every verify run away from production. It is a Playwright test fixture plus a config: journeys import `test` and `expect` from `guard.ts`, never from `@playwright/test`, and run only with this folder's `playwright.config.ts`.

## What it does

- **Before the browser opens**, `loadSettings` refuses to start when the backend is a name other than this machine and has no pin, or when:
  - `VERIFY_SETTINGS` or `VERIFY_RUN` is not set, or the settings file is missing;
  - `backend` is empty or is one of `blockedHosts`, or `blockedHosts` is empty;
  - `devServer` is not on this machine;
  - the settings name no `localFile`, the local file is missing, `rewrite` is not a list of origins, or `alsoAllow` names an address that is not on this machine.
- **A pinned backend:** when the safe backend uses the same name as a real server (the developer's hosts file points it at this machine), set `pinBackendTo` to the loopback address that serves it (`127.0.0.1` or `::1`; check with `curl -H "Host: <name>" http://127.0.0.1/` and `http://[::1]/`, because a local web server can serve a different site on each). Chromium then resolves that name to the pin itself (the name is left out of the resolver's exclusions, which would otherwise win over the pin), a pin cannot be combined with `rewrite` (Playwright would look the rewritten name up again outside the browser), and `global-setup.ts` refuses to start before any browser when Node resolves the name anywhere but this machine. Leave `pinBackendTo` empty for a backend on `localhost`. Because Launch starts the dev server before any Playwright run, Doctor's first part makes the same check by hand: `node -e "require('node:dns').promises.lookup(process.argv[1], { all: true }).then((a) => console.log(a.map((x) => x.address).join(' ')))" <backend name>` must print only loopback addresses (`127.x.x.x`, `::1`). Run it where the dev server resolves names: inside its container or virtual machine when it runs in one, since that has its own hosts file.
- **Name resolution:** the config starts Chromium with a host-resolver rule that resolves only this machine, the backend's host and the `alsoAllow` hosts, and with `--no-proxy-server`, so a proxy set on the machine never receives a request and resolves its name elsewhere. Any other name fails to resolve. This covers redirects the browser follows, workers, popups and any extra context, so a host the route misses still cannot be reached.
- **During a run**, every request the page makes goes through one route:
  - to `devServer`, `backend` or an `alsoAllow` origin (another port on this machine, such as a local file server; never a remote host): sent as it is;
  - to an origin listed in `rewrite` (the backend the app's own settings name): fetched from this machine's `backend` (the local file) by Playwright, without following redirects, and handed back to the page. An old commit whose settings name a production host still talks only to the allowed backend;
  - anything else: blocked.
  Requests a journey sends itself through Playwright's HTTP client (`page.request`, `context.request`, the `request` fixture), which the browser route never sees, follow the same rules in `guardRequests`: allowed origins as they are, `rewrite` sources to the backend, both without following redirects, anything else refused and logged; `run.mjs` also removes proxy variables from Playwright's environment. Read a state back through these or through the page, never through another HTTP client.
  WebSocket connections are allowed only to the same origins and closed otherwise. Each rewritten, failed (the backend did not answer a rewritten request) and blocked request is written to `network.log` in the run's folder, as method and origin only: never a path or query, because apps put personal data there (a login check with the e-mail in its query, for example).
- **The login** comes only from `loginFile`, an ignored local file the owner fills (`KEY=value` lines; `loginKeys` names the keys). It is never written into a journey, the settings or a committed file; a capture or log that shows it is fine, because the account is a restricted throwaway one. Traces stay off and the reporter stays `list` (run.mjs refuses others): a trace or an HTML report is a large extra artifact the evidence does not need. Journeys get 180 seconds.
- Service workers are blocked, and only Chromium runs, because the host-resolver rule is a Chromium setting.

## Limits

- **Redirect hops.** Playwright does not run the route for the second and later hops of a redirect. The resolver rule still keeps every hop on this machine or the allowed hosts, but a hop to another port there is not checked by the route. The guard watches every hop it is told about: one outside the allowed origins (rewrite sources included, since a hop is never rewritten) is written to `network.log` as `escaped` and fails the run, so its evidence never counts. Playwright reports no request event for a page's favicon, so a favicon redirect is not seen; the resolver rule still keeps it on this machine.

- **The dev server's own proxy.** The guard allows everything sent to `devServer`. When the app's dev server proxies paths to a backend (for example an Angular `proxy.conf.json` or a Vite `server.proxy`), Doctor must read its targets and refuse when any target is not the allowed backend: a target on the blocked list and an unlisted remote API alike, because the browser only sees the dev server's own address. The same holds for a dev server that calls a backend itself (server-side rendering, API routes). What the dev server and the local backend do on the server side (a request, a redirect they follow) is outside the browser, so the guard never sees it: Doctor's first part searches their settings and environment files for every blocked host and refuses when one is named, and the backend must be a local copy that calls no production service. Doctor reads these settings before Launch, on the checkout about to start, because Launch's first page request already runs them.
- **Cookies and CORS after a rewrite.** The page still sees the original address, the response comes from the allowed backend. A token login carried in a header works. A login that depends on cookies may not, and the backend must allow the dev server's origin. Doctor proves one logged-in call through the rewrite before any journey counts.
- **Another driver.** A journey that imports `@playwright/test` directly skips the route; one that calls `chromium.launch()` skips the route and the name rule. Doctor checks that every journey imports only from the guard.

## Machine values

`settings.json` is committed and holds only what is the same on every machine. `localFile` names an ignored file (for example `.env.verify.local`, covered by a `.env.*` ignore rule) with this machine's values; copy `verify.local.example`:

- `VERIFY_BACKEND`: the local backend address on this machine.
- `VERIFY_PIN_BACKEND_TO`: the loopback address for a backend whose name is also a real server, or empty.
- `VERIFY_DEV_SERVER`: another dev server address, or empty for the one in `settings.json`.

Without the file the guard refuses to start and names what to fill in. Never write a machine's host names in the skill text or the committed settings.

## Set it up in an app

1. Check the app's installed `@playwright/test` is 1.65 or newer (`node node_modules/@playwright/test/cli.js --version`): the guard was built and type-checked on 1.65.1, and explore needs `browser.bind` and the CLI's `attach`. With an older one, stop and ask the developer to update it; never install on your own. Then copy `guard.ts`, `global-setup.ts`, `playwright.config.ts`, `run.mjs`, `drive.mjs` and `redact.mjs` (they find each other through the folder of the `settings.json` that `VERIFY_SETTINGS` names, so keep them next to it) into `.claude/skills/verify-<app>/`, and `explore.spec.ts` with a filled-in `prepare.ts` into its `journeys/` folder.
2. First do step 3's check, before the machine settings file or the login file holds anything. Then copy `settings.example.json` to `.claude/skills/verify-<app>/settings.json` and fill it with what is the same on every machine: the dev server port, every production host the app's settings files name (except a name the owner points at this machine and pins with `VERIFY_PIN_BACKEND_TO`: that name is the backend, kept on this machine by the pin, and the guard refuses a backend on the blocked list; when that pinned name is the app's only production name, `blockedHosts` stays empty, which the guard accepts only with a pin), the list of hosts the app's own settings call that must be sent to the backend (`rewrite`), the ignored login file and key names, the screen size and touch of its users, the ignored artifacts folder, and `localFile`. Then copy `verify.local.example` to that `localFile` and fill this machine's backend there; the committed settings never hold a backend.
3. Check that the login file, the machine settings file (`localFile`) and the artifacts folder are each ignored (`git check-ignore -q <path>` for every one, exit 0 meaning ignored; never decide on `-v`, which also exits 0 for a path a `!` rule re-includes; the artifacts folder as `<artifacts>/` with a trailing slash so a folder-only rule matches before the folder exists; a rule for one never stands for another). Do not change the project's ignore rules without the owner's OK.
4. Each run gets a new name (`VERIFY_RUN`); the run claims a new folder `<artifacts>/<run>/` for its `network.log`, videos and screenshots, and refuses a name already used, so one run never wipes another's evidence. A one-off journey (for one bug) is an input, written before the run in `<artifacts>/journeys/<run>/` (the default when `VERIFY_JOURNEYS` is unset), never in the run folder and never in the tracked skill folder. Journeys that belong to the map (the setup check) may live in the skill folder; point `VERIFY_JOURNEYS` at them.
5. Run from the repository root, so `@playwright/test` resolves from the app's own `node_modules`:

```
VERIFY_SETTINGS=.claude/skills/verify-<app>/settings.json VERIFY_RUN=<name> VERIFY_JOURNEYS=.claude/skills/verify-<app>/journeys node .claude/skills/verify-<app>/run.mjs --grep-invert "explore:"
```

Always run journeys through `run.mjs`, never `npx playwright test` directly: it starts Playwright with the skill's config and keeps its exit code, and it takes only journey files and the options `--grep`, `-g`, `--grep-invert`, `--list`, `--repeat-each`, `--headed`, `--max-failures`, `-x` and `--timeout`, refusing every other option (another reporter, trace, UI, config, output folder, browser or project, snapshot or source updates), so a run never leaves the guarded Chromium, skips the guard's config or writes outside the ignored artifacts folder; screenshot baselines go to the run folder too. The runner cannot stop a journey's own code from writing elsewhere, so a journey writes every screenshot or file itself to `testInfo.outputPath('<name>')`, never to a plain path.

`--grep-invert "explore:"` leaves out the explore session, which waits for a stop file; start it only as "Explore step by step" says. `VERIFY_DEVICE=desktop|mobile` and `VERIFY_VIEWPORT=<width>x<height>` override the settings' device and window for one run (explore or journey), for a report from another kind of device; `VERIFY_DEVICE` alone also takes that device's usual window (Playwright's Pixel 7 or Desktop Chrome).

On Windows PowerShell set the variables first: `$env:VERIFY_SETTINGS = "..."; $env:VERIFY_RUN = "..."; $env:VERIFY_JOURNEYS = ".claude/skills/verify-<app>/journeys"` (without `VERIFY_JOURNEYS` the run looks in the one-off folder `<artifacts>/journeys/<run>/`).

## Explore step by step

`explore.spec.ts` runs like a journey, so the same guard, pin, video and login apply. It runs the app's `prepare.ts` (log in, open the start screen; copy `prepare.example.ts`), shares the browser under the run's name, writes `explore.md` in the run folder with the attach command, and waits until a file named `stop` appears in the run folder (or `VERIFY_EXPLORE_MINUTES`, default 30, pass).

1. Start it in the background, from the repository root: `VERIFY_SETTINGS=<skill>/settings.json VERIFY_RUN=<new name> VERIFY_JOURNEYS=<skill>/journeys VERIFY_EXPLORE_MINUTES=30 node <skill>/run.mjs explore.spec.ts`. The runner prints Playwright's output when the session ends. The session binds the browser under a unique name (`Session:` in `explore.md`), which the driver reads, so two runs never share a browser.
2. Wait for `<artifacts>/<run>/explore.md`; it lists the exact commands. If it never appears and the run ends, read the run's output: a missing login or local file stops the session before it starts.
3. Drive only through the verify driver, from the repository root: `node .claude/skills/verify-<app>/drive.mjs <run> attach`, then `... <run> snapshot`, `... <run> click <ref>`, `... <run> screenshot`, one action at a time. The driver runs Playwright's CLI with the run's session and with the run folder as its working folder, so snapshots and screenshots land there.
4. Stop: create `<artifacts>/<run>/stop`. The session then writes `explore-result.md` (`ended: stopped`); a session that expires or loses its page fails and says so. The video of the whole session is saved under `output/`.

The driver allows only screen actions and read-only looks: attach, detach, snapshot, find, eval, screenshot, click, dblclick, fill, type, press, keydown, keyup, hover, select, check, uncheck, drag, mouse actions, resize, dialog-accept, dialog-dismiss, goto, go-back, go-forward, reload, tab-list, tab-select. Every argument that starts with `-` is refused (no `--config`, other session or output file), `goto` takes only an http or https address, and a run whose session ended is refused. Before and after each command the driver cuts query strings and fragments from every full web address the CLI prints and from each snapshot link value (`/url:`) in the files it saves in the run's `.playwright-cli` folder (`redact.mjs`, shared with explore), because apps put their own tokens and reset links there; other text is left as the page shows it. The CLI's console logs are deleted, because Playwright keeps appending raw addresses to them between commands; read console messages through `eval` when a check needs one. When the session ends, explore unbinds the shared browser and cleans the folder once more, and Cleanup deletes the run's `.playwright-cli` folder after the explore run has exited; a failed unbind or clean fails the session. `eval` stays for read-only measurements (a box, a class, a computed style): it must never change the page, storage or state. It refuses everything else, among them `run-code` (Node code outside the browser), `route` and `unroute` (could remove the guard's routes), `state-save` and `state-load` (would write the login session to a file), `request`, `request-body` and `request-headers` (could show the login request), network, storage and cookie changes, tracing (stores typed text) and `close-all` or `kill-all`. It is a guard against mistakes, not against an agent that runs other commands on purpose: never call Playwright's CLI directly in a verify run. Playwright's CLI also keeps its own session registry and daemon files in its tool cache outside the repository; that is Playwright's, not evidence.

The test account is a restricted throwaway account made for the agent (verify-app SKILL.md, Setup check), so its login is not hidden from the run's output or files; what keeps it in its place is that it is read only from the ignored login file in `prepare.ts`, never typed into a command, a prompt or a committed file, and that the run folder sits in the ignored artifacts folder. Fill the login fields the ordinary way (`fill`, or typing), as a user would.

## Prove it

Part of the setup check, recorded with the commands:

1. In a folder of its own under the artifacts folder, copy `settings.json` with `localFile` pointing at a file there that holds `VERIFY_BACKEND=` a production host as an https address and no `VERIFY_PIN_BACKEND_TO`; when that host is not in the copy's `blockedHosts` (the pinned-name case, where the real list leaves it out or is empty), add it there in the copy only; run `node <skill>/run.mjs --list` with `VERIFY_SETTINGS` on the copy (the runner takes the config and helpers from its own folder, so only the settings come from the copy): it stops with "is a production host; refusing to start" before a browser starts. Delete that folder afterwards.
2. Run a journey that opens a page and requests an address that is not allowed: the request fails in the page and appears as `blocked` in `network.log`.
3. Start an explore session, run `drive.mjs <run> attach` and `drive.mjs <run> snapshot` (the snapshot shows the app's start screen), then from the attached driver `drive.mjs <run> goto https://example.org/verify-guard-probe`: the navigation must fail as blocked and `network.log` must show `blocked GET https://example.org`, which proves the attached browser is the guarded one (a navigation, not a `fetch` from the page, so an app's Content-Security-Policy cannot stop the probe before the guard sees it); then `drive.mjs <run> go-back`. Then create the stop file: `explore-result.md` says `ended: stopped`, the run exits 0, and the session's video is in the run folder's `output/`.
