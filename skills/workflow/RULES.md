# Rules readiness before workflow work

Resolve the installed local `rule-maker` skill (not an upstream specialist). Read its `rules/START.md`, `rules/CORE.md` and `rules/READINESS.md`; load only relevant framework modules. Reading those references is not permission to run setup. Missing local library: disclose and pause affected work; do not invent a substitute or fetch/install silently.

Before substantive planning, task scaffolding, application edits or output-producing/delegated work, establish the readiness state. Bounded read-only discovery is allowed first. No previous rule-maker invocation or marker is required when existing applicable rules are adequate. Empty, unreadable, stale or conflicting guidance is not adequate merely because AGENTS.md exists.

If coverage is missing, stop and offer: prepare a minimal setup, a specific bounded exception with named consequences, read-only investigation, or stop. Setup permission and application implementation permission are separate. Unknown trust, identity, authority and safety conflicts are not covered by a generic exception. Reuse valid scoped decisions after rechecking affected inputs; do not re-ask every task.

Use the existing task/checkpoint for a compact state/source/scope record, not a new report. Apply the same rule on resume, direct utilities, scope changes and subagents. `codebase-design` and other specialists receive the effective rules and cannot redesign around them. Unknown gate states stop affected changes. The shared readiness reference is authoritative; this file only routes to it. Apply POLICY.md to conflicting memory/current instructions; a full rules audit uses rule-maker/AUDIT.md, not a readiness pass.

## Select engineering and version guidance

After establishing readiness, use rule-maker's VERSIONS.md to distinguish declared requirements, locked dependencies, actual runtime and project structure. Its optional version_facts.py helper collects static facts only; unsupported or conflicting resolution needs inspection, not a guessed pass. Select conditional modules through ENGINEERING.md for the change's actual data, lifetime, reliability, testing, security, performance and compatibility risks. These complement, not replace, Matt's specialists. No module selection authorises installs, upgrades or unrelated cleanup. Load operations.md before side-effecting checks: verify prerequisites, build permission, effective backend/isolation and quiet-host requirements; report actual evidence rather than an assumed GREEN status.

Pass the relevant rules, installed-version evidence and approved exceptions to plan/design/code reviewers and workers. Keep meaningful scope/verification notes in existing records; no per-function compliance checklist or report per module. Recheck affected inputs after a dependency or shared-rule update, preserving valid approval unless its substantive agreement changes.

## UI boundary before dependent planning

For application UI (including markup/behaviour, not only stylesheets), the shared design.md routes to installed local ui-design. Establish mode, approved source/variant/pattern scope and preview authority; record them compactly in existing task records. A selected approved existing component/pattern can suffice without a full kit. Missing presentation coverage blocks UI integration; no plain-HTML fallback. Missing/disabled ui-design blocks affected UI work unless an equivalent strict-reuse procedure is explicitly approved; do not bypass host disabling. Scope/defaults never weaken stricter project restrictions. Backend-only work skips the UI route. The local codebase-map renderer retains its approved report styling, not permission for styled application prototypes.
