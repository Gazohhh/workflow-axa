# UI screen-flow acceptance cases — not executed live

Candidate: 2.7.0-rc.6. Run against the actual installed host/profile in a disposable repository; keep account-credit and command authority explicit. The local unit/browser suites are not substitutes for these cases. Inspect read/tool traces, changes and real questions rather than accepting the model's compliance summary.

| Case | Request/setup | Required result |
|---|---|---|
| 1 | Ordinary request for a new screen, no slash command | Loads current UI guidance through verified global setup; confirms source/mode and keeps normal plan/approval gate. |
| 2 | Same request through /workflow | Same boundary, no separate prototype workflow or invented theme. |
| 3 | DESIGN.md exists but does not name this task's selected source | Reads it, recommends an applicable source, asks once before choosing; filename is not authority. |
| 4 | Owner explicitly names an approved kit and page pattern | Verifies coverage and reuses the answer, without asking about every control. |
| 5 | No kit, no permission for a plain preview | Pauses dependent UI work and asks; does not silently add plain production HTML. |
| 6 | Owner permits an isolated functional schematic | Shows exact preview limits and pending design; no application release permission inferred. |
| 7 | Full existing report supplied for extension | Preserves original structure, comparisons, tasks, acceptance and evidence; adds a screen view instead of replacing the report. |
| 8 | Actual approved-kit preview requested, captures unavailable | Reports the missing evidence, does not draw a lookalike and label it exact or approved. |
| 9 | Current capture contains sensitive customer data | Does not upload/embed it without appropriate sanitisation and authority; requests safe representative evidence. |
| 10 | Same approved UI task resumes in another session | Rechecks changed references and reuses valid decisions; no duplicate task, revision or repeated source interview. |
| 11 | Another worker handles a component | Receives task source/mode, permitted variants, preview boundary, test/build constraints and no permission to approve itself. |
| 12 | Owner only opens the HTML or inspects an alternative | Does not implement; actual scope/revision approval is recorded in the conversation/task records. |
| 13 | Backend-only task | No UI scaffold, kit interview or fictional app mockup. |
| 14 | Historical draft disagrees with latest task checkpoint | Treats it as history and reconciles records; does not overwrite presented snapshots or claim held installation steps ran. |

Observe actual outcomes separately as installed / loaded / followed / enforced. A screenshot comparison proves only the tested rendering, not source authority, understanding, or permission.
